# Inbox parity audit

## Baseline

At 1264×1258 in the existing headed browser, authenticated external Linear t2 opened `https://linear.app/cloverve/inbox/priority` and `/inbox/other` (read-only); authenticated local Hoja t1 opened `http://127.0.0.1:8790/workspace/inbox`; isolated t4 remains open. The worktree is substantially dirty/untracked and includes prior frontend/server changes. Local Inbox currently renders a dashboard: Open issues/In progress/Completed/Active projects metrics and all ten loaded issue rows, including items unassigned to this user. There was no `notification` table, Inbox GraphQL query, read/archived state or unread count at inspection. Existing `issue_activity` records mutation events but is not a recipient notification feed. No external Linear mutation was attempted.

## Comparison

Linear Inbox displayed heading, unread sidebar badge, Priority and Other tabs with counts, read/unread notification rows naming issue/event/actor/time, unread-only toggle, Add filter (type, subscription, sender, project, priority, status), Display options (priority, badge, grouping, ordering, snoozed/unread-first), and Notification actions (mark all read, delete variants, settings). Clicking Priority/Other changed route; unread-only toggled to Show read. Menus were opened read-only; no notification was marked/deleted. A priority onboarding panel was visible. The loaded visible Linear rows included overdue, issue completion, comment and project-added events, plus onboarding; the exact prioritization algorithm and full counts could not be inferred from the small visible sample. Hoja showed none of these notifications and instead showed ten issues with no read state. Linear-only old history, subscription/mention/reaction/project notification sources and priority training require additional data/semantics; do not synthesize them.

## Source map

`frontend/src/main.tsx` lines 17–18 route Inbox via sidebar and lines 36–50 render dashboardContent and metrics, not notifications. Existing `gql()` at line 16 handles authenticated GraphQL; `openIssue()` at line 21 navigates. Backend `cliniar_server/db.py` lines 273–281 defines `issue_activity` but no per-user notification table; `writer.py` lines 152–159 records events; `store.py` lines 688–710 scopes Activity to assignee/creator/actor but not read state. `schema.graphql` Query/Mutation at lines 45–85 has no Inbox contract. Feasible: generate future issue notifications for relevant non-actor recipients transactionally, page by stable cursor, mark read/archive, unread count, local unread-only/Recent grouping and issue navigation. Not feasible as exact Linear parity: historical notifications, external mentions/subscriptions, cloud sources, genuine priority ranking or snooze/preferences without additional models. The database revision needs migration; take a backup before touching the original database and restart only the local service after schema checks.

## Backend

Schema revision 10 adds `inbox_notification` with organization, recipient, issue, actor, kind, timestamp, read and archive fields (`cliniar_server/db.py` lines 284–296, migration map). The writer generates notifications transactionally for a non-actor assignee/creator when an issue is created or changed, including reassignment (`writer.py` lines 161–170,221–226,267–272). Self-authored actions do not notify the actor. `schema.graphql` lines 55–56,76–78,102–111 exposes `inboxNotifications(first,after,unreadOnly,archived)`, `inboxUnreadCount`, and read/archive/mark-all actions. Store/resolvers scope every row/action by authenticated org and recipient, sort by timestamp+ID descending with a cursor, return pageInfo, and make repeated marking idempotent (`store.py` lines 689–740; `resolvers.py` lines 123–175). This is a future-event notification feed, not retroactive issue history. Unsupported sources (mentions, external integrations, project/agent/customer events) are not fabricated. A fresh isolated revision-10 schema and build_schema/compilation passed. Before original migration a SQLite online backup was taken at `~/.local/share/cliniar/hoja.pre-inbox-rev10.backup.db`; original migrated 9→10 and only local `hoja-web` was restarted to load the new schema. The original Inbox has no historical notifications, as expected. A focused isolated multi-user flow confirmed issue-create delivery to recipient (unread 1) and no sender self-notification (unread 0); no unit tests were added or run.


## Frontend

`frontend/src/main.tsx` now routes `/workspace/inbox` and its `/priority` or `/other` child paths to a dedicated `InboxPage` (`main.tsx` lines 70–101) instead of the generic recent-issues dashboard. It queries recipient-specific notifications and unread count, renders item title/issue/actor/kind/time, native issue navigation, read/archive, mark-all-read, unread-only and load-more; route tabs keep URL selection. Priority is visibly labeled as chronological fallback, not an invented ranking. Unsupported Linear filter/display/delete/snooze controls are omitted rather than faking persisted behavior. Client guards stale unmounted/filtered requests, dedupes pages, validates cursor progression and retains loading, empty, retry/error states. The unread badge is the server's actual recipient unread count, not loaded-issue count; existing issues are not retroactively converted. CSS after the project issue styles owns desktop/mobile feed layout, row focus, counts, menu, and honest empty. One backend shape correction was necessary: GraphQL read/archive/all mutations return Boolean directly, so the client queries Booleans and checks them, not `{success}` objects. Opening an issue does **not** silently mark it read in this implementation; explicit Mark read is required. This distinction is documented, not claimed as Linear parity.


## Verification

On original Hoja t1 `/workspace/inbox` after revision 9→10 migration and local server restart, the Inbox showed “No notifications yet,” not ten loaded issues. Priority and Other tabs changed URL/selection; Priority carried an explicit ranking-unavailable notice; unread-only showed “No unread notifications,” and Mark all read was disabled at count zero. No original historical notifications were fabricated. A separate isolated browser fixture at `http://localhost:8802/workspace/inbox/other` (different cookie hostname and database) had two members: an issue created by Sender for Recipient produced one unread notification for Recipient and zero for Sender. Browser showed issue title/actor/kind and badge 1. Mark read changed badge to 0 and read styling, persisted after reload; unread-only became empty; Archive removed the read item and persisted after reload. A later issue-title update generated one new unread recipient notification; a separate unassigned issue later assigned by Sender to Recipient generated exactly one new unread item, with Sender unread still zero. The browser item navigated to the issue detail and Back restored Inbox; Mark all as read changed badge 1→0 and persisted after reload. A subsequent second fixture update yielded two unread rows; keyboard focus+Enter on Mark read reduced 2→1, unread-only showed one row, and Mark all read reduced 1→0 with all three visible rows read after reload. Priority/Other browser routes switched selection and Back restored Other with the same unread count; at 390px row/tab controls fit without horizontal overflow. Browser errors were empty; sampled GraphQL requests returned 200, local route HTML and `/ready` returned 200/ready. External Linear t2 remained read-only; tabs t1/t2/t4 plus isolated t5 were kept. No unit tests were added or run. A forced failed-request path and full 50+ cursor pagination were not browser exercised.


## Result

Inbox was **not finished** before this pass: it was an issue dashboard, not notifications. It now supports a real future-only, recipient-scoped issue notification feed, persisted read/archive/all-read actions, unread count, navigation, pageInfo and an honest empty state. The original account remains empty until a different actor changes/assigns work involving it; this is expected rather than a failed migration. An isolated two-member browser flow verified create/update recipient delivery, explicit read, archive, mark-all, reload persistence and responsive layout. `VERSION`/`pyproject.toml` are 0.16.0 with a changelog. Remaining Linear differences: no historical backfill, mention/comment/project/agent/customer/onboarding event sources, true Priority ranking/training, filters, notification settings, snooze, delete variants, or automatic mark-read-on-open. No 1:1 parity claim. Pre-existing dirty backend/frontend/docs changes were preserved; scoped additions are in `cliniar_server/db.py`, `writer.py`, `store.py`, `resolvers.py`, `schema.graphql`, `frontend/src/main.tsx`, `styles.css`, version/changelog and this document. No commit/tag/release or external Linear mutation was performed.
