# Initiatives parity audit

## Baseline

Persistent headed browser at 1264×1258 and 390×844: t2 authenticated external Linear `https://linear.app/cloverve/initiatives/active`, `/planned`, and `/initiatives` (read-only); t1 authenticated local Hoja Test Workspace `http://127.0.0.1:8790/workspace/initiatives` displays “Initiatives is not available in Hoja yet.” t4/t5 isolated fixture tabs remain open. The worktree contains substantial pre-existing dirty/untracked server, frontend, docs and version files; preserve all. External Linear has no visible initiative rows in this account at the inspected states, so populated list/detail layout is not established.

## Comparison

Linear Initiatives header has a New initiative action, Active, Planned and All initiatives tabs, Add filter and Display options. All three views showed an empty explanation (“Initiatives are larger, strategic product efforts…”) and create/documentation controls; Planned labels its empty state “Upcoming initiatives.” The Add filter menu exposed AI/Advanced, Status, Priority, Owner, Creator, Contributing teams, Labels, Health and Dates. Display options exposed grouping, ordering and toggles for ID, Description, Owner, Status, Priority, Contributing teams, Health, Projects, Active projects, Target/Created/Updated/Completed dates, Labels. Opening New initiative (without submitting) exposed required initiative name, summary, status, priority, owner, target date and labels, with Create disabled while name empty. At 390px tabs and heading remained visible without horizontal overflow. The empty account cannot establish populated row ordering, actual project membership, owner permissions, initiative detail or filter effects. Hoja has no list/create UI, API, storage or initiative-project relation at baseline. Do not represent projects as initiatives or claim 1:1 semantics from this empty reference.

## Source map

`frontend/src/main.tsx` lines 18 and 47 own sidebar route and placeholder; `gql` at line 16 supplies authenticated requests. `cliniar_server/schema.graphql` Query/Mutation and `db.py` tables contain projects but no initiatives; `resolvers.py` uses `_ctx` for org/user scope; `store.py` and `writer.py` are org-scoped read/write analogues. Implement a distinct initiative entity and project association with authenticated workspace scope, plus list/create/update and real empty/tab states. Stable pagination must be implemented explicitly; `_conn` defaults pageInfo.hasNextPage false. Finer Linear AI filters, priority/health aggregation, historical activity and populated visual parity are unobserved/unsupported; do not invent them.

## Backend

Revision 11 introduces an organization-scoped `initiative` and `initiative_project` relation (`cliniar_server/db.py` lines 282–306, migration map line 538). GraphQL `initiatives(first,after,status)` and `initiative(id)` with `Initiative` fields, plus `initiativeCreate`, `initiativeUpdate`, `initiativeArchive` are declared in `schema.graphql` lines 34–35, 61–62, 95–98, 270–272. Store `initiatives`/`initiative_by_id` (`store.py` lines 828–840) filter organization and archived state, order newest timestamp/ID, and serialize actual project associations; resolver `r_initiatives` (`resolvers.py` lines 266–278) returns a real pageInfo cursor rather than relying on `_conn`. Writer initiative methods (`writer.py` lines 154–202) validate name/status/priority, owner and same-org active project references, create/update/archive transactionally, and avoid duplicate association inserts. Missing/foreign initiatives are not exposed or updated. No projects are recast as initiatives and no historical rows are generated. A fresh isolated SQLite migration reached revision 11; Python compilation and GraphQL schema construction passed. Migration of original Hoja will use a backup and local server restart before browser verification. Full cross-tenant/50+ pagination and permission-gated roles remain unverified; no unit tests are added or run.


## Frontend

`frontend/src/main.tsx` now routes `/workspace/initiatives/active`, `/planned`, and `/workspace/initiatives` to a separate `InitiativesPage`, not the placeholder (component after `IssueDetailPage`). It queries authenticated `initiatives(first:50,after)` with real pageInfo, dedupes cursors, discards stale unmounted results, and renders Active/Planned/All tabs, the observed empty explanations, create and documentation actions. Add filter supports a real local Status filter; Display options toggles Description only, explicitly disclosing unsupported Linear grouping/ordering. The create form follows observed name/summary/status/priority/owner/target-date inputs and adds project association backed by the new relation; Create stays disabled until a nonblank name. A successful create refreshes list; errors remain in the draft form. Native links/buttons and responsive CSS after the Inbox rules support keyboard focus and 390px viewport. Because Linear's account had no populated rows, the simple Hoja list shows real name/status/projects/date but does not claim identical populated layout or computed health/progress. No fake initiative rows are generated from projects.


## Verification

At original local t1 `http://127.0.0.1:8790/workspace/initiatives` after rev10→11 migration and server reload, the placeholder was replaced by the Initiative header, three tabs, Add filter, Display options, empty explanation and create action. Planned tab navigated to `/workspace/initiatives/planned`, selected Planned and showed **Upcoming initiatives**; Active showed the generic empty. Status filter and Description display controls opened without errors. The create form opened with Name, Summary, Status, Priority, Owner, Target date and the existing local project checkbox; Create was disabled while name empty, Close dismissed without mutation. The original initiative table had zero rows at that point. Linear t2 was inspected read-only with the same empty tabs/menus; no external initiative was created. The first local browser query failed because GraphQL Initiative lacked `createdAt` while the frontend requested it; adding the field to SDL and restarting the local service recovered the empty state. A separate isolated t6 fixture at `http://localhost:8803/workspace/initiatives` (not original Hoja DB) created a Planned initiative with name/summary through the visible composer: blank-name Create disabled, focus+Enter submitted, All and Planned showed its row, Active remained empty, and Planned row persisted reload. Status filter Active on All yielded a no-match message and Clear restored one row; Display Description toggle hid/restored summary. At 390px all tabs and the row fit without horizontal overflow; browser error/console captures were empty, sampled local GraphQL returned 200, the served route returned HTML 200 and `/ready` returned ready. Exact populated Linear layout remains unavailable. No unit tests were added or run.


## Result

Initiatives now has distinct tenant-scoped persisted records and a responsive browser-visible Active/Planned/All view, create form, status filter, description toggle and honest empty/loading/error states. The original Hoja workspace remains empty, matching its data; a separate isolated fixture verified one real Planned initiative and reload persistence. Version is 0.17.0 (`VERSION`, `pyproject.toml`, `CHANGELOG.md`). This is **not 1:1 functional or visual parity**: Linear's reference workspace had no populated rows, so populated list/detail layout, manual ordering, advanced/AI filters, health/labels/contributing teams, initiatives' historical updates and complex strategic rollups are unobserved or unsupported. The project relation exists but linked-project pagination and a full detail editor are not browser-verified. Pre-existing dirty work and external Linear data were preserved; no unit tests, commit, tag or release.
